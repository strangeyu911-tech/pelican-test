# 决策记录 v1.0

> `PLAN_v1.0.md` 里列了 5 个需要拍板的问题，外加 1 个"跑完再定"的帧率问题。
> 这里记录最终结论、依据，以及**改了之后连带影响什么**。
> 后 3 个版块的人不需要重读计划书，读这一页就够。

---

## D1 · Intro 用几小节 → **3 小节（6 秒）**

**理由**：原需求的 2.5 小节会让 Intro 结束在 5.0 s，而 120 BPM 的小节线在 4.0 / 6.0。
5.0 s 落在第 3 拍上 —— 于是 20 次穿画框全部错开半小节，每一格"梗"那一拍都会歪。
用 3 小节后 69 条小节线全部对齐，`V.TL.boundaries` 里每个值都是 2 的整数倍。

**代价**：总时长 137 → **138 s（2:18）**。比需求的"约 2:17"多 1 秒。

---

## D2 · 1000×1000 是核心构图区 + over-scan → **是**

单位空间 1000×1000 映射到屏幕的 1080×1080，两侧各溢出 420 px 给镜头推拉与视差。
**连带铁律**：`V.ROAD_Y = 838`、`V.RIDER_X = 360` 全片不许改，否则穿画框时人会跳。

---

## D3 · 版块时长统一 3 小节 → **不统一，按内容分配**

| 版块 | 小节 | 理由 |
|---|---|---|
| song（宋山水） | 4 | 要"先看不见鹈鹕，镜头推近才看见"，3 小节不够推 |
| code（代码美学） | 4 | SVG 要一行一行写出来，写完还得留一拍看结果 |
| tang（唐白描） | 2 | 只有一条线在飘，3 小节会拖 |
| bada（八大山人） | 2 | 只有一个白眼，多了就泄气 |
| 其余 16 格 | 3 | 进场 / 梗 / 离场各一拍 |

> 早先我建议从 8-bit 那格抽 1 小节，这是错的 —— 8-bit 要装下"跳坑 + 吃金币 + 1UP"
> 三个动作，本来就紧。这 1 小节从两个最简单的墨戏格子里出。

## D4 · 帧率 → **母版 60 fps，草稿 30 fps**

同一段 3 秒（含一次穿画框），同样 3 worker：

| | 30 fps | 60 fps |
|---|---|---|
| 帧数 | 90 | 180 |
| 渲染耗时 | 10.5 s | 13.3 s |
| 每秒渲染帧数（含启动） | 8.6 | 13.5 |
| 3 秒片段体积（crf 18） | 0.5 MB | 0.7 MB |
| 整片体积 | 21.6 MB | 28.9 MB（1.34×） |
| 整片渲染耗时（8280 帧） | — | 约 6 分钟 |

**决定用 60** 的理由不是"更高更好"，是这片子有个具体的痛点：

路面滚动速度 466 单位/秒 ≈ **503 px/s**（1080p）。
- 30 fps → 每帧跳 **17 px**
- 60 fps → 每帧跳 **8 px**

地面是细颗粒砂石，17 px/帧的位移会读成明显抖动（"轮子在搓地"而不是"在滚"）。
60 fps 的代价只是体积 1.34 倍、渲染时间翻倍（6 分钟），可以接受。

**草稿仍用 30**：迭代时没人看抖动，只看节奏和构图，速度快一倍。

> 对比素材：`out/ab_30v60.mp4`（左右并排）、`out/ab_30v60_slow.mp4`（4 倍慢放，
> 采样差异肉眼可辨）、`out/pelican_rough_30fps.mp4` / `_60fps.mp4`（整片两版）。
